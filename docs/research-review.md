# 1. 完全没被调研、但对本项目至关重要的领域

## 1.1 QRC/LRC 时间轴 → MV 音轨的重锚定算法（最严重的缺口）

至少 6 个地方写了「必须做全局 offset + 逐句漂移校正」「这不是可选项」，但**没有任何一个领域调研过怎么做**。缺的具体东西：

- 全局 offset 怎么估：人声 onset 检测？分离后 vocals 与 QRC 首字时间的互相关？还是用行级锚点做 RANSAC 拟合仿射变换？
- 是单一 offset、分段线性，还是需要 DTW warp（MV 有额外前奏/间奏剪辑时必然是后者）
- 怎么判定校准失败并把该段落降级为「需人工确认」

这块是「有 QRC」和「能用 QRC」之间的唯一桥梁。没有它，QRC 全链路实测跑通也交付不了第一个视频。

## 1.2 文本度量闭环（注音定位）——被三个领域各自列为"待实测"，无人负责

ASS 领域、注音领域、前端领域都说「注音必须自己算 x 坐标」「用 HarfBuzz」「与 libass 是否像素一致未验证」。但没人调研那条唯一能真正闭环的路径：**直接问 libass 要度量**。

具体可行方案没被评估过：
- ctypes/cffi 封装 `ass_render_frame`，渲染一行到内存，读 `ASS_Image` 链表的 `dst_x/dst_y/w/h` 反推包围盒；
- 或用 ffmpeg `-vf ass=...:alpha=1 -frames:v 1` 渲染到透明帧，用 numpy 求 bbox。

这两条都是本地、跨平台、且**定义上就与最终渲染一致**的。调研全程在纠结「uharfbuzz 能否近似 libass」，而没人问「能不能直接用 libass 本身」。这是本项目最大的单点技术风险（注音错位 = 日式卡拉OK 观感崩塌），却零调研。

## 1.3 编辑器状态层：撤销/重做、项目持久化、崩溃恢复

彻底没有。而这是三级调轴 UI 的骨架：
- undo/redo 栈怎么和「强制对齐重跑」共存？重跑是一个 undo 单元还是 N 个？
- 项目文件格式（JSON? SQLite?）、schema 版本迁移、自动保存节流
- 用户调了 40 分钟轴，进程崩了怎么办

调研里反复强调「一站式」「三级调轴 UI 就是核心功能」，但核心功能的状态管理一个字没有。

## 1.4 后端长任务编排

零碎提到「子进程」「-progress pipe:1」「WebSocket/SSE」，但没有系统调研：
- 任务队列（单机自研 vs arq/dramatiq）、取消语义（kill 子进程后临时文件谁清）
- 并发闸门：Demucs（几 GB 显存/内存）+ ffmpeg 烧录 + JASSUB 预览同时跑会 OOM
- 工作区/临时文件生命周期与磁盘预算（一首歌：原视频 + 音频 + 2 条 stem + 代理视频 + 成片 ×2，轻松 3-5 GB）
- 缓存键设计（分离领域给了 `(audio_sha256, model_id, backend_version)`，但没推广到对齐/烧录）

## 1.5 音视频时间基准的正确性

完全没调研，且是会咬人的真实坑：
- yt-dlp 合并出的容器 `start_time != 0`（非零起始 PTS）时，ASS 绝对时间会整体偏
- VFR / YouTube VP9 的时间戳；烧录时是否强制 CFR
- 分离/对齐用的 16 kHz mono 与原始 44.1 kHz 立体声之间，重采样滤波器延迟是否引入 offset（几 ms 级，但会叠加到「50-150 ms 对齐误差」上）
- 音频提取的起点是否严格等于视频起点

调研里所有时间轴讨论都默认「时间就是时间」，没人验证过这个前提。

## 1.6 分行/断句策略与段落（间奏）检测

- QRC/LRC 的官方分行 ≠ nicokara 一屏两行的分行。兜底领域只说了「UI 要提供拆行/并行」，但**自动分行算法零调研**（按时长间隔？按全角字符数 12-20？按语法边界？），拆并行后时间怎么重分配也没定。
- 段落检测 nicokara 领域给了固定阈值 4.0 s 并自己承认对慢歌会误判。没人调研用分离出的伴奏/人声 VAD 能量来做——而你**本来就已经有 vocals stem**，这是免费的更好信号。指示灯（4 点倒计时）是 nicokara 的标志性元素，判错段落就等于判错指示灯。

## 1.7 对唱声部归属（diarization）

两个领域都说「必须手动标记」「本地没有可靠方案」，但**没人真去查**。至少这几条值得评估而没被评估：
- `pyannote.audio`（本地推理，模型在 HF 需接受条款）在分离后 vocals 上的表现
- 先用 `mel_band_roformer_karaoke_*` 分 lead/backing，再按能量归属
- QQ 的 `singingAnnotationsLyric` 字段（对本曲为空，但格式与覆盖面未查）

验证曲目正好是男女对唱，且 nicokara 对唱分色是明确需求。「承认存在」不等于「调研过」。

## 1.8 字体覆盖检查（缺字静默 fallback）

只在 nicokara 领域的「待实测」里出现一次。这是个 20 行的检查（用 fontTools 读 cmap，扫描全部歌词字符 + 注音假名），但缺失后果严重：预览和导出可能 fallback 到**不同**字体，直接摧毁 WYSIWYG。应该是硬性 pre-flight check。

## 1.9 环境自检 / 首次运行体验

没有系统设计。桌面工具必须开机自检：ffmpeg 是否带 libass、libass 版本、torch 设备、模型是否已下载、字体是否齐、磁盘余量。分离领域只零星提了一句「把 `torch.cuda.is_available()` 打给用户看」。

## 1.10 测试与回归策略

调研里散落着 60+ 条「必须实测/必须做像素回归/必须写单测保证不变式」，但**没有任何一处调研怎么执行**：
- headless 跑 JASSUB 截图（Playwright？）与 ffmpeg 单帧做 SSIM 对比的 CI 方案
- 对齐精度的 ground truth 标注工具（对齐领域说「人工标 20 个假名起点」——用什么标？）
- 端到端 smoke test 的素材与断言

而且这 60+ 条「待实测」没有优先级排序，也没有一条可执行的验证顺序。

# 2. 互相矛盾的结论

## ⚠️ 矛盾 A：QRC 覆盖率 → 三种对立的架构优先级

| 领域 | 结论 |
|---|---|
| QQ音乐 | 「20/20 命中，『新歌覆盖不到』的担忧不成立」 |
| 强制对齐 | 「不要指望任何歌词库给出逐字轴，**强制对齐是主生产模块而非校正模块**」 |
| 验证素材 | 「歌词源反而是最富裕的一环，强制对齐应从『生成时间轴』**降级为局部精修**」 |

这三个直接决定第一版先做哪条路径、投入比例如何。而且推翻记录已经指出：**赤春花 2026-01-29 就数字先行配信了，MV 才是 07-23，QQ 入库时间是 2026-02-27**——也就是说「两周新歌冷启动」这个场景**从来没被验证过**，三方都在用一个不成立的样本论证。这个矛盾必须裁决，且需要换一首「只有 MV、无同步商业发行」的真新歌重测。

## ⚠️ 矛盾 B：[kana:] 数据在三个领域是三种东西

| 领域 | 对 [kana:] 的定位 |
|---|---|
| QQ音乐 | 「逐汉字读音 + 逐音拍时间，注音编辑器的初始值，用户只需微调」 |
| 歌词兜底 | （断言被推翻）「非独有、是无锚点流式启发式、覆盖率未知、**本地 MeCab 兜底管线仍是必需项**」 |
| 日语注音 | **四层模型（L0 自动 / L1 JmdictFurigana / L2 用户词典 / L3 实例覆盖）里根本没有这一层** |

注音领域的作者显然不知道 QRC 已经提供了带时间的官方 kana。四层优先级模型必须重构成五层，且「歌词源 ruby」的优先级应高于 JmdictFurigana（前者是该曲的实际演唱读音，后者是通用词典读音，歌词里大量当て字场景下前者更准）。

## ⚠️ 矛盾 C：Kugou vs QQ 谁做主源

两个领域给出完全相反的 provider 排序（QQ 第一 vs Kugou 第一），两边的推翻记录都承认「没做同曲对比」。这是半小时能裁决的实测问题，却悬着。

## ⚠️ 矛盾 D：注音读音（kana）与对齐读音（pron）的衔接断裂

注音领域讲得很清楚：`reading_display`（表记读法，用于 ruby）与 `reading_phonetic`（发音形，喂 G2P/对齐）必须**同时存在**，混用是系统性 bug 源。

但：如果注音来自 QQ 的 `[kana:]`，你只拿到了 display，**pron 从哪来？** 助词「は」在 kana 轨里标的到底是「は」还是「わ」不确定，长音、「ん」的音位变体都无法从假名串确定性还原。`pyopenjtalk.g2p` 吃纯假名串时的行为被注音领域列为「待实测」——而这恰恰是整个「注音与对齐共享读音」方案能否成立的关键节点。没人把这两条线接上。

## ⚠️ 矛盾 E：mora 定时 vs QRC 字级定时——数据模型的核心冲突

- 注音领域的不变式：**「时间轴单位永远是 mora」**，surface 字符块的 `\k` = 其所属 mora 时长之和
- QRC 给的是 **surface 字符级**时间：`学(t1,d1)校(t2,d2)`
- 强制对齐输出的是 **mora 级**

从 QRC 导入时，你**无法**把「学(t1,d1)」精确拆成「が/っ/こ/う」四拍——只能按比例分，而这正是注音领域明令禁止的伪造粒度。两种来源产生两种粒度的数据落进同一个模型，谁向谁转换、如何标记「这段 mora 时间是插值出来的」，无人裁决。这是数据模型层面的硬冲突，会在第一次「QRC 导入 + 注音显示 + 逐拍走字」时立刻暴露。

## ⚠️ 矛盾 F：描边翻色的实现方案

- nicokara 领域：「必须双层 + 渐进 `\clip`」，且推翻记录进一步说「**纯 ASS 目前没有任何已验证方案**能做到描边同步翻转」
- ASS 领域：「能用 `\t` 表达的就一个音节一行」「逐帧展开性能可接受」

两边**同时**把结论挂在同一个未验证问题上：**libass 是否支持 `\t(t1,t2,\clip(矩形))` 动画**。ASS 领域自己列了「`\t` 只有矩形版 `\clip` 能动画」——而水平扫光恰好只需要矩形版。也就是说答案很可能是「支持」，写一个 20 行的 ASS 文件跑一次 ffmpeg 就能定，却没人跑。**这是第一个视频能不能有 nicokara 观感的决定性问题。**

## 矛盾 G：libass 版本约束（三处结论应合并为一条硬性构建规则）

- 前端领域：JASSUB pin 到 libass master commit `266b9831`（0.17.5 之后 22 个 commit，含线程架构重写，**无任何 tag 覆盖**）
- 打包领域：「自建 LGPL-only ffmpeg，`--enable-libass`」（未指定版本）
- 合成领域推翻记录：真正决定 `\blur` 的是 `LayoutResX/Y`（依赖 `ass_layout_res()`），不是 `PlayResX/Y`

三条合起来的唯一正确结论：**ffmpeg 侧必须 vendor 与 JASSUB 完全相同的 libass commit**，「>= 0.17.5」是不充分的。没人下这个结论。

# 3. 标了"已验证"但仍然可疑的

**① 「20 首日语曲 20/20 命中 QRC」（标 high）**
样本全部是「主流与中腰部 J-POP」，全部有正规商业发行——**样本选择偏差就是被测变量本身**。同一个人同一天同一套代码跑的，无交叉验证。且只验证了「有 QRC 字段」，未验证 QRC **逐字质量**（Kugou 领域明确把「逐字轴是人工打还是机器生成、误差多大」列为未验证）。应降为 medium 并注明「覆盖率结论仅适用于有商业单曲发行的曲目」。

**② 「MV 时间轴与录音室母带几乎完全重合，差 11 ms」→「偏移校正是全局单一常数，不要写复杂重对齐逻辑」（标 high）**
这是用 **YouTube 官方句级人工字幕** 对比 **网易句级 LRC** 得出的。两者都是人手打的句级时间轴，本身就有 ±100 ms 的随意性——**用两份人工标注的一致性去证明两条音频轨的时间基准一致，推理不成立**。验证素材领域自己在「待实测」里也承认「需实测比对波形」。但选型建议已经据此给出了架构指令。这条结论应作废，改由波形互相关重测。**这是被写进架构建议的、建立在无效推理上的结论，风险最高。**

**③ 「QRC 端到端解密跑通」——两个领域直接对立**
QQ音乐领域：「解密成功，10926 字符 QRC XML，首句 `桜(774,665)舞(1439,188)...`」（标 ✅已验证）
验证素材领域：「**没有真正看到解密后的 XML**，标准 DES 9 次全败，这是整个 QRC 链路唯一未闭环的一环」

两条都自称本机实测。这必须立刻裁决——如果 QQ 领域是对的，把那段代码固化下来；如果没跑通，整条主链路的地基是空的。

**④ 「JASSUB `setEvent` 增量更新是 60fps 拖拽的前提」**
前端领域明确标了「**未实测**，若单次超 16 ms 需改成『拖动时 DOM overlay 预览、松手才 setEvent』的双层策略」。但选型建议已经把它写成「整个『一站式』的技术前提」。未验证项被当成了前提。

**⑤ 「karaskel 注音算法可直接照抄」**
已被推翻（两趟遍历、遗漏 `0<furiwidth<=basewidth` 分支的 spill、符号解析在 `preproc_line_text` 而非 `do_furigana_layout`）。但修正后的版本仍然依赖 `aegisub.text_extents` 的等价物——**又回到 §1.2 的度量闭环问题**。也就是说这条「已修正」的结论，其可用性仍然悬在一个未解决的前置问题上。

**⑥ Tauri `externalBin` 的 macOS notarization issue #11992**
推翻记录里提到了，但被埋在细节中。这是**分发路径上的潜在阻断项**（配了 externalBin 就公证失败，无 workaround），应该被提升到架构决策层，而不是当作一个脚注。

**⑦ 「pyopenjtalk-plus 的 macosx_10_13_universal2 wheel 覆盖 arm64」**
理论正确（universal2 含 arm64 slice），但没实测 pip/uv 在 arm64 上是否正确选中该 tag。风险低但属于「推论被标成实测」。

# 5. 证据已足够、但无人拍板的架构决策

## 🔴 必须由用户拍板（阻塞至少 5 个选型）

**D0. 产品最终是「私有自用」还是「对外分发二进制」？**
这个问题直接决定：ffmpeg GPL/LGPL 构建路线、LDDC/pykakasi/qqmusic-api-python(GPL) 能否直接用、MMS_FA / ctc-forced-aligner 权重(CC-BY-NC)能否用、Roformer 权重能否打包、是否要花 $99/年 + Windows 签名。至少 5 个领域都在「若要分发则…」里打转。**这是第一优先级待决策项。**

## 🟢 证据充分，可以直接定

**D1. 中间数据模型是唯一真源，ASS 只是渲染目标。**
四个领域独立得出同一结论。但**模型本身有四个不兼容版本**（QQ 的 `LyricsDoc`、兜底的 `LyricCandidate/Syllable`、注音的 `Line/Token/Mora`、前端的「边界数组」）。必须合成一个正式 schema——这应该是写第一行代码之前的第一件事。

**D2. 时间轴内部单位 = 毫秒整数**，存**边界数组**（`token[i].tEnd === token[i+1].tStart`，同一个值），ASS 厘秒只在序列化时产生，且用「对累积时间点取整再取差」而非逐个 round。三个领域独立得出，可定。

**D3. libass 是产品依赖，锁 commit，两端同源。** ffmpeg 必须 vendor JASSUB 使用的同一个 libass commit（当前 `266b9831`），不是「>= 0.17.5」。同时锁 freetype/harfbuzz/fribidi。升级 JASSUB 必须同步重建 ffmpeg + 跑像素回归。

**D4. 显式写 `LayoutResX/LayoutResY` = 输出分辨率**（不只是 PlayRes），显式写 `ScaledBorderAndShadow: yes`，两端才不会在 `\blur` 上分叉。这是合成领域推翻记录里唯一正确的机制解释，应写进 ASS 生成器的硬性规则。

**D5. 「重计算作业」的通用架构**：独立子进程 + JSON-lines 进度协议 + 按 `(input_hash, params, version)` 缓存 + 可取消。分离领域已给出，应推广到强制对齐、烧录、峰值计算——它们有完全相同的约束。

**D6. 横切的 `(value, source, locked)` 元数据模型。**
注音领域的 L3 `locked`、对齐领域的 `syllable.locked + source: auto|manual`、兜底领域的「来源徽章」、前端领域的边界数组——**这是同一个机制的四个视角**。应抽象成横切设计：任何自动产生的值（读音、注音、时间边界、分行、声部归属）都带 `(value, source, locked)`，任何重算只覆盖 `locked=false`，UI 用颜色区分来源。这个结论证据充分，但没人抽象出来。配套的「token 内容寻址身份键 + 重绑失败清单」（注音领域已给出）应一并采纳。

**D7. Provider 抽象**：provider 只负责取回并归一化，选择交给 resolver（打分维度：粒度 × 时长差 × 标题/歌手模糊匹配 × 官方推荐标记）；**粒度可提升不可伪造**；来源徽章必须可见。兜底领域已给出完整设计，可直接采纳。

**D8. 注音是派生量，不是存量。** 独立 `\pos` Dialogue，坐标随字体/字号/字距变化重算；度量由**单一实现**产出（建议后端 uharfbuzz 或 libass 绑定），前端只消费坐标，绝不用 Canvas `measureText`。

**D9. 默认导出 libx264 CRF 18-20 preset medium/slow**；硬编（videotoolbox/NVENC）只作「快速预览」档位。

**D10. ON/OFF VOCAL 只烧一次视频**，再用 `-c:v copy -c:a aac` remux 两条音轨。

**D11. 模型权重运行时下载**（独立进度条 + SHA256 + 断点续传 + 支持离线导入 + `HF_HUB_OFFLINE`），绝不打进安装包。三个领域一致。

**D12. 明确写进 non-goals：不做纵书（縦書き）。** libass `\kf` 在旋转/纵向下扫光方向错误（issue #293/#406，未修）。证据充分，早点砍掉比后期发现好。

**D13. 按设备能力选默认分离模型**：macOS arm64 / Windows+NVIDIA → BS-Roformer；Windows 纯 CPU → 降档 htdemucs 或 MelBand，并在 UI 明示预计耗时。

**D14. 第一天就配 COOP/COEP**（Vite `server.headers` + Tauri `app.security.headers` + FastAPI 的 `Cross-Origin-Resource-Policy: cross-origin` + `<video crossorigin="anonymous">`）。前端领域已经说了「不要等后期加 Tauri 壳才发现」——但这条建议本身没被提升为决策。

**D15. 音频永远走 Web Audio 双 stem 混音**，`<video>` 永远静音、作为从动方。前端领域论证充分（W3C 明确指出 media element 间无法保持同步），可定。

---

**一句话总结**：调研的**深度**很好（尤其对抗验证抓出了大量夸大结论），但**广度有系统性偏斜**——所有精力都花在「外部依赖能不能用」上，几乎没有花在「这个应用自己怎么组织」上。缺的四块拼图（重锚定算法、度量闭环、描边翻色实测、编辑器状态层）里有三块不需要联网调研，只需要写 50 行代码跑一次实验。**在补更多外部调研之前，先花半天把这三个实验做掉。**
