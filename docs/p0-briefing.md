# 决策简报：做出第一个视频的可行路径

日期 2026-08-09 ｜ 基于 6 路并行实测 + 对抗验证后的净结论。凡对抗验证推翻的部分，以修正值为准。

---

## 一、QRC 链路的最终裁决

### 裁决：**通。第一版歌词走「QRC 现成逐字轴 + 人工微调」，强制对齐从第一版链路中整体移除。**

支撑这个裁决的三条硬证据（均经独立复现）：

1. **解密闭环成立且不可辩驳**。魔改 DES（SBOX2[23]=15、SBOX4[53]=10，加取位宏字节逆序、PC-2 的 D 半区偏移 −27）是必需的，标准 3DES 解出的确是垃圾。最强证据不是自洽性，而是**跨信源交叉验证**：未经任何解密的明文 LRC（`fcg_query_lyric_new.fcg`）与解密后的 QRC，在 kana 轨 503 字符、ti/ar/al、60/60 行正文上完全相同 —— 排除了"解出自洽垃圾"的可能。脚本可重复运行，17 个产物逐字节 md5 一致。
2. **粒度是真逐字，且是单个书写字符级**。633 块中 99.1% 为单字符；6 个多字符块全是 ASCII（`sumika` / `ikura)` 等）；**日文正文无任何多字符块**，汉字与送假名各自独立成块。第二个数确认是 duration（相邻越界 0 次）。泛化到 アイドル 同样 99.1%。
3. **强制对齐在第一版无必要**。既然逐字轴现成，就不需要 `reading_phonetic`、不需要 wav2vec2（1.26 GB）、不需要 CTC 后处理、不需要 §5.5 整节。这是本轮最大的工作量削减 —— 两条路差一个数量级，而我们拿到的是省掉数量级的那条。

### 三条必须同时写进裁决的限定条件

- **覆盖率结论仍只对"有商业发行的曲目"成立**。2026-07-31 的 niconico 同人曲在 6 个源上 **0/6 全灭**，YouTube 也只有自动字幕。CLAUDE.md §5.2 关于样本选择偏差的警告完全正确，本轮用实数确认了它。**强制对齐兜底路径不能删，只能推迟到 v1.1**（第一版不实现，但数据结构必须留 `timing_source=aligned` 的位置）。
- **`[kana:]` 的逐拍时间是"机会性标注"，不是 provider 给了 mora 时间轴**。同一个汉字在同一首歌里时有时无（`桜` 10 次里 9 次有、`春` 13 次里只有 3 次有）。正确口径：需要拆拍的多拍汉字共 116 个，其中 61 个有时间 = **52.6%**（不是 34.3%，那个分母错了）。且 61 条全部无拗音，只能称"逐假名字符时间"，不能称 mora。**架构上只能做"有则用、无则回退插值"的增强层，不可依赖。**
- **QQ 的正式搜索端点当前可用，CLAUDE.md 的记载已过时**。`DoSearchForQQMusicDesktop` 从本机（境外 IP、无代理、无 Cookie）返回 20 条完整结果，两个独立 agent 分别复现（一个还用「周杰伦」做了对照组）。lyrics-sources 报告的"结果集恒为空"是错的。

### 附带裁决：主源用 QQ，不是酷狗

lyrics-sources 的"酷狗为主源"结论**被推翻**，三条理由都是致命的：

| 项 | 声称 | 复测实况 |
|---|---|---|
| 酷狗独立曲逐字获取 | 2/2 | **1/2**（さびしさ 候选数 0，它自己的 JSON 就写着 `found_candidate: false`）—— 报告把 `search.found`（搜到歌）当成了"拿到逐字歌词" |
| QQ 独立曲 | 0/2 | **1/2**（五月雨 以 `Samidare` 收录，QRC 9968 hex，且带 roma+trans；さびしさ 有歌无词）——与酷狗打平且多两条轨 |
| 酷狗 UGC | "独立曲特有的质量层级" | Lemon 16 个候选、アイドル 20 个候选**全部是 ugc**，5 首里只有验证曲有官方推荐歌词。以酷狗为主源＝绝大多数曲目拿到用户上传歌词 |

**优先级定为**：QQ QRC 主源（逐字 + kana + roma + trans，解密已闭环）→ 酷狗 KRC 并列第二（交叉校验，必须按 `product_from` 优选而非取 `candidates[0]`）→ 网易云 / LRCLIB 行级兜底 → UtaTen 单独接入做 furigana 权威源（与时间轴解耦，4/4 命中）→ YouTube 官方 ja 字幕仅作加分项，**必须逐曲探测，不能按热度假设**（Lemon 与 アイドル 都没有人工 ja 字幕，验证曲反而有）。

## 二、第一个视频的最短可行路径

前提：目标是把 `HCC-0sr_-lo`（赤春花 MV）做成带逐字扫色 + 振り仮名的 ON VOCAL 成品。

| # | 步骤 | 状态 | 依据 / 注意 |
|---|---|---|---|
| 1 | yt-dlp 下载 MV，remux 为 mkv | **已验证可行** | 无 cookie / 无 PO Token / 31 formats。**必须改**：显式 `format-sort` 取高码率（默认按编码器偏好选了 4.2 Mbps AV1，放弃了 12.3 Mbps VP9）；**必须记录实际写入容器的 format_id**（现有 report 记的是探测阶段的 best，与实际下载的流不一致） |
| 2 | 探测容器 `start_time` / CFR | **已验证可行** | 本样本 start_time=0。**但非零分支已实测会咬人**：构造 start_time=5s 的容器后，默认参数抽出的 wav 直接短 5s —— ffmpeg 静默吃掉偏移。必须显式核算 |
| 3 | QQ 搜索定位 songmid | **已验证可行，但过滤器有洞** | 正式端点可用。**必须补曲名精确匹配**：现有"歌手含 sumika + 时长≈260s"过滤后剩 2 条（赤春花 260s + 无关的 チョコレイト 259s），取 `cands[0]` 命中纯属侥幸 |
| 4 | 拉取并解密 QRC / roma / trans | **已验证可行** | 三条轨全部解密成功，可直接固化进 provider 层 |
| 5 | 解析 QRC → 逐字块 + 剥离制作名单 | **已验证可行** | 剥离规则 5/5 命中、误伤 0、漏剥 0。**两个新坑必须遵守**：`LyricContent` 用正则 + `html.unescape` 取（XML 解析器会把 60 行压成 1 行）；kana 的覆盖数 N 按单个数字解析（`\d+` 会把 `111111` 读成一个 N=111111） |
| 6 | 由 `[kana:]` 生成注音行 | **待实现（算法已验证）** | 假名锚点切分手工用例 16/16、歌词全量降级 0。但 §5.6 规划的主力方案 **JmdictFurigana 完全未测**，「手紙→てがみ」这类无假名锚点词目前只能整词一个 ruby（实测占 2.6%，第一版可接受） |
| 7 | 全局 offset：下 Art Track 做模式 A | **已验证可行** | Art→MV = **+61.9 ms**、constant、25/25 分段一致、NCC 0.860。独立方法（GCC-PHAT）复测 +61.137 ms。下载成本 4 MB / 4 秒 |
| 8 | 把 offset 应用到 QRC 轴 | **仍有风险 —— 这是本路径唯一的软肋** | 见下节。第一版做法：应用 +62 ms，然后**必须人工试听确认首句**，UI 出全局 offset 滑块 |
| 9 | 生成 ASS（双层 + 渐进 clip 描边翻色） | **待实现（方案已验证）** | `\t(t1,t2,\clip(...))` 实测严格线性推进，每句 2 个 Dialogue 即可 |
| 10 | 注音行布局（`\pos` + advance 度量） | **待实现（方法已验证）** | 用尾随标记块反推 advance，全角恒定；注音居中于 **advance 格位**而非墨迹包围盒；`Fontsize ≠ em size`（字号 72 → advance 50px） |
| 11 | ffmpeg-full 烧录 | **待实现** | `ffmpeg_locate.find_ffmpeg_with_libass()` 已可用，但**端到端烧录本轮无人跑过** |
| 12 | （可选）OFF VOCAL 轨 | **已验证可行** | 整曲实测：htdemucs **20.1~20.7 s**、BS-Roformer **62.3~64.6 s**（283.8 s 曲目 / M5 Max / MPS / 热缓存，波动 ±3%）。第一个视频若只做 ON VOCAL，可整步跳过 |

**关键判断：第 1–7 步全部已验证，剩下的全是"待实现"而非"待实测"。** 也就是说，第一个视频不再有需要先做实验才能动工的环节，只有第 8 步需要一个人工确认动作。

必须在生成 ASS 时处理的三个已知细节：**19 个 dur=0 的半角空格块**（正是 libass #124 触发条件，必须合并或改 `\kt`）；`\k` 厘秒取整必须用"下一块起点倒推"而非逐个 round；ASCII 连续段整体成一个 `\k` 块。

## 三、仍然阻断的事项（按严重程度）

**1（最严重，但可绕过）：歌词轴 → MV 的绝对锚定没有可信的自动手段。**
模式 A（音频↔音频）可靠到亚毫秒，但它需要两条音频；歌词轴不是音频。模式 B（歌词脉冲串↔音频）在真实素材上峰值 0.09 vs 负对照 0.01~0.04，**检测统计量完全分不开**，只能出候选值。所谓"三方闭环误差 1.6 ms 证明模式 B 其实是对的"是错的 —— MV 音频就是 Art 音频整体延迟 62 ms，两条相关曲线是彼此的平移副本（平移 64 ms 后相关系数 0.929），闭合是恒等式，零证据价值。
**还有一个未解释的矛盾**：若 QRC 轴对准母带、Art Track 即母带，则 QRC→Art 应≈0，实测却是 −67.9 ms。要么模式 B 不可信（大概率），要么 Art Track 有前置静音。**这个矛盾没被任何实验解决。**
绕过方式：走 Art Track 模式 A 拿 +62 ms + 人工试听确认。62 ms 在人耳可察阈值以下，第一个视频不会因此崩掉。但这条**必须写进产品预期**：找不到 Art Track 的曲目，重锚定无法自动落轴。

**2：ASS 生成 → 烧录整条尾链一行代码都没有。** 双层 clip、advance 度量、`\pos` 布局各自验证过，但从未组装过，也从未有一帧画面被渲染出来。这是当前最大的**工作量**风险（不是技术风险）。

**3：冷启动新歌全灭（0/6）。** 已确认不是猜测。这条不阻断第一个视频（赤春花是最佳样本），但阻断产品可用性。v1.1 必须补强制对齐 + 手动粘贴路径。

**4：模型下载器必须自建。** `audio-separator` 的 `download_file_if_not_exists()` 无 SHA256、无 Range 续传，幂等性仅靠 `os.path.isfile` —— **下载中断留下的半截文件会被永久误判为"已下载完成"**，且默认落 `/tmp`。已观测到多 agent 各自建目录重复下载 723 MB。

**5：Windows 侧零实测。** 全部结论来自 PyPI 元数据。`torch-directml` 的真实阻断点是硬钉 `torch==2.4.1`（项目用 2.13），不是"不支持 Python 3.12"（那是声明性元数据，pip 不会拒绝）。

**6：JASSUB `setEvent` 延迟（P1-5）、JmdictFurigana（P2）、对齐精度 ground truth（P2-11）、自动分行（P2-12）** —— 全部未动。前者是"一站式"的技术前提，仍未验证。

## 四、需要用户拍板的问题

1. **第一个视频接受"全局 +62 ms + 人工试听确认"吗？** 若要求全自动可靠对齐，第一个视频就要等一轮新实验（真实 vocals 上复跑模式 B，看峰值能否越过可判定阈值）。**建议：接受人工确认，先出片。**
2. **主源确认 QQ 而非酷狗？** 本简报按 QQ 主源给出，与 lyrics-sources 的原始建议相反。请确认。
3. **第一版是否砍掉强制对齐整章（§5.5）？** 砍掉可省 1.26 GB 模型 + phonetic 推导 + CTC 后处理，但意味着第一版对"无歌词源曲目"完全无能为力。**建议：砍掉实现，保留数据结构位置。**
4. **第一个视频要不要 OFF VOCAL 轨？** 不要则整个人声分离步骤跳过；要则 +20 s（快档）或 +63 s（最佳档）。
5. **下载质量取向**：显式指定取高码率 VP9（12.3 Mbps）还是接受默认 AV1（4.2 Mbps）？前者文件更大、解码更重，后者是成片母版的质量损失。
6. **`audio_44k.wav` 命名约定**：按源采样率命名（本曲实为 48 kHz）还是固定名 + 强制重采样到 44.1 kHz？现在名实不符。

## 五、对 CLAUDE.md 的修订建议（具体到章节）

### 可以结项的"待实测"

| 章节 | 项 | 处理 |
|---|---|---|
| §9 P0-3 | QRC 解密闭环 | **标「已实测」结项**。裁决：解密成功一方正确；"标准 DES 九种全败"同时也正确，两者不矛盾。DES 表可直接固化进 provider 层（纯 Python，6032 字节耗时可接受）。**补一个回归测试**：固定 lyric.hex 前 64 字节 → 断言 SHA256 |
| §9 P0-4 | 重锚定 | **部分结项**。模式 A 成立并给出四态裁决；模式 B 判定为"不可自证，只出候选值"，**保留为开放项**（待真实 vocals 复测） |
| §9 P1-7 | `pyopenjtalk.g2p` 吃纯假名串 | **结项：不能确定性推导**。它会把假名串完整重跑形态素分析，继承分词歧义（ははは→ワワワ），且平/片假名走两条路径 |
| §9 P2-9 | Kugou vs QQ 主源 | **结项：QQ 主源**（理由见 §一） |
| §9 P2-10 | 冷启动新歌覆盖率 | **结项：0/6 全灭**，已用真实样本（VOCALOID 同人曲）验证。样本量 n=1，建议再补 1 首 |

### 必须修正的既有结论

- **§4.2「粒度冲突的裁决」**：确认 QRC 权威粒度为 surface 字符级（补入 99.1% / 日文正文无多字符块的实测数字）。**新增一段**：`[kana:]` 携带机会性逐假名字符时间，覆盖 52.6% 的多拍汉字，这部分标 `timing_source=provider`，其余走插值；**明文禁止在架构上依赖它**（同字不一致，12 个字自相矛盾）。同时标注：五条不变式中第 2 条（`mora.surface_span` 归属）与第 4 条（相邻边界严格相等）**仍未验证**，第 1 条在现有实现下是构造恒真、不构成检验。
- **§4.5 末段**：删除「这条路径能否走通取决于 g2p 的行为，见 §9」，改写为已定结论 —— **phonetic 的权威来源 = 对汉字原文做形态素分析取 `pron`**；`[kana:]` 只覆盖 `reading_display`；两者冲突的 token 标 `needs_review`。补充：真正无法用规则恢复的只有两类 —— 促音便（`もう一回` 的 `一` read=イチ / pron=イッ）与跨 token 长音化（`ゆこ`+`う`→ユコー）；漢語/和語判别可由 UniDic `goshu` 字段解决，不是不可判定项。
- **§5.2 Provider 表**：QQ 行状态由"解密闭环未裁决"改为"**已实测端到端闭环**"；优先级列填入裁决结果。**新增一条铁律**：酷狗候选必须按 `product_from`（官方推荐歌词 > ugc > 第三方）优选，不得取 `candidates[0]`；并注明实测 5 首中仅 1 首有官方歌词。
- **§5.3**：整节的"待实现的设计方向"替换为已实测的四态裁决（constant / linear / piecewise / needs_manual / no_match）与阈值（残差 p90 ≤30 ms 判模型成立、台阶 ≥160 ms 判分段、80 ms 报警）。**断点定位精度必须诚实写为 ±5~15 s（半个到一个半分段步长），只够粗定位**。明确写入模式 A / 模式 B 的能力边界，并**禁止把"三方闭环"当作真值检验**。新增管线步骤：**自动检索同曲 Art Track**（成本 4 MB / 4 s，把不可靠变可靠）。
- **§5.4 档位表**：用整曲实测值替换所有推算值 —— htdemucs 20.1~20.7 s、BS-Roformer 62.3~64.6 s（283.8 s / M5 Max / MPS / 热缓存），**快档与最佳档真实差距 3.1 倍**。加一条方法论硬规则：**禁止用 30 秒片段线性外推整曲耗时**（实测两个方向都错，误差达 60%）。DirectML 排除理由改写为"硬钉 `torch==2.4.1`，与项目 torch 2.13 冲突"。
- **§5.6 表格**：形态素分析器默认明确为 **fugashi + unidic-lite**（UniDic 26 字段原生同时给 `kana`/`pron`，与数据结构一一对应）；**SudachiPy 降级为「新词补充源，仅供 reading_display」**（已枚举确认其 Morpheme/WordInfo 无任何发音形字段）。`jaconv` 本轮实际未被使用，可从必需清单移出。补注：`unidic-lite` 零 wheel 仅 sdist 属实，但它是纯数据包无 C 扩展，**不构成 Windows 装机风险**（此前的担忧过重）。
- **§5.14**：明确"**必须应用层自建下载器**"，并写明上游缺口的具体后果（半截文件被永久误判完成）。要求：`*.part` + 原子 rename + 自算 SHA256 基线清单 + Range 续传 + 显式 `model_file_dir` 指向 `platformdirs.user_cache_dir()`。补注 `list_supported_model_files()` 会发网络请求，离线自检需处理失败。
- **§6.1 版本混淆条目**：双条件过滤**不足**，必须补曲名精确匹配（±3 s 时长窗会放进同专辑其他歌）。另加：**频道显示名不具区分力** —— MV 与 Art Track 的 channel 显示名同为 "sumika official"，必须比对 `channel_id`。
- **§6.1 搜索端点条目**：`DoSearchForQQMusicDesktop` 的"境外 IP 结果集恒为空"**已过时**，两个 agent 独立复现返回 20 条完整结果。同时标注 `search_for_qq_cp` 的"已验证可用"**存疑**（本轮尝试报 `code=500003` 参数错误，未跑通）。保留"访问层必须可换端点 + 可挂代理"的要求 —— 这些都是时间快照。

### 需要补进陷阱清单的新坑

**§6.1（歌词源）**
- `LyricContent` **绝不能用 XML 解析器取**：其行分隔符是字面 0x0A，XML 属性值规范化会把它替换成空格，60 行直接压成 1 行、逐字行数变 0。必须用正则 `LyricContent="(.*)"\s*/>` 取原文再 `html.unescape`。（注意：这与现有那条"必须先反转义"是两回事，不能合并）
- `[kana:]` 的覆盖数 N **必须按单个数字解析**，`\d+` 贪婪匹配会把连续的 `111111` 读成一个 N=111111 的条目 —— 这正是既有 DECO*27 整体错位坑的机制。
- 酷狗 `krcs` 候选**绝大多数是 UGC**，`candidates[0]` 盲取会拿到用户上传轨。

**§6.2（时间轴与对齐）** —— 这一节末尾那条"未调研的时间基准问题（会咬人）"现在可以**部分结项，且证实全都会咬人**：
- **同一个 YouTube 视频的不同音频 format，原点可以不同**：MV 的 opus(251) 与 aac(140) 实测相差 **+36.7 ms**（两条独立方法测得 36.66 / 36.28 ms，且与 Art→MV 的 61.1 ms 严格自洽：61.137 + 36.281 = 97.418）。**硬性规则：下载、分离、重锚定、烧录必须锁同一个 format_id，工程文件里记录它；换 format 必须重跑重锚定。**
- **ffmpeg 默认抽音频会静默吃掉容器起始偏移**：构造 start_time=5 s 的容器后，`-vn -acodec pcm_s16le` 抽出的 wav 时长 = 总时长 − 5 s，wav 的 0 时刻等于容器 start_time 时刻。必须显式探测并核算（或统一 `-copyts` / `-avoid_negative_ts` 策略）。
- **opus 的 `initial_padding`（312 样本）+ 末包裁剪会让 wav 比容器短约 24 ms**。单独看可忽略，但会与其他误差叠加，逐字对齐层面应显式记账。
- **CFR 判据不可用"pts 间隔标准差 < 0.5 ms"**：mkv 毫秒 time_base 的量化本身就产生 0.455 ms 抖动（余量仅 9%），且帧间隔恰为 x.5 ms 的帧率会被误判为 VFR。应改用有理数帧率比对。

**§6.3（渲染）**
- **QRC 中存在 dur=0 的块（本曲 19 个，全部是半角空格）**，正是 libass #124 的触发条件。生成 ASS 时必须合并进相邻块或改用 `\kt`，不能原样输出 `\k0`。
