# 界面重新规划（2026-08-09 拍板）

本文是前端信息架构的重做规格。实现以本文为准；与旧代码冲突的地方一律以本文为准，
不要为了少改代码而保留旧结构。

---

## 一、现状为什么杂乱

问题不在于某个面板难看，而在于**中间舞台被硬编码了**。

`frontend/src/App.tsx:193-200` 把主区域写死成"预览 + 时间轴"，与当前处于哪一步无关；
每一步真正的操作面板则被塞进左侧那条窄导航的 `workflow-nav__content` 里
（`App.tsx:166-190`）。后果是：

- 搜歌词时，需要逐条读、逐条比的候选挤在窄栏里，而屏幕最大的一块摆着一个此刻毫无用处的播放器
- 注音、样式这类需要"看清楚才能确认"的功能，被降级成右侧一个窄 tab
- 播放控制在多处重复出现，因为没有任何一处是它的正当归属
- 每一步都长得一样，用户无法从画面本身判断自己在做什么

**根因是一条错误的默认假设：视频播放器是本工具的中心。** 它不是。视频只是背景；
本工具的中心是歌词——它的文本、读音、时间轴和样式。播放器只是若干步骤中恰好需要的一个器件。

---

## 二、核心原则

> **中间舞台属于当前步骤的主对象。**

"预览 + 时间轴"只是**编辑**这一步的舞台形态，不是全局外壳的一部分。每一步自己决定
中间怎么分栏、要不要播放器、要不要波形。

派生出三条硬性规则：

1. **每一步都必须能在中间大区域看到它的主对象**——素材看素材、歌词看歌词、样式看样式。
   任何"主对象在窄栏、无关物在大区域"的排布都是错的。
2. **播放控制归属于当前舞台**，全局不设播放器。同一时刻界面上只存在一个 transport。
3. **应用外壳保持低饱和**，把颜色预算留给两处：成片预览的真实配色，以及来源徽章
   （CLAUDE.md §7.4 要求 `provider` / `aligned` / `interpolated` / `manual` 在界面上可见地区分）。

---

## 三、外壳

左侧窄导航**整个取消**。步骤条移到顶栏，中间舞台因此拿到全部横向空间。

```
┌───────────────────────────────────────────────────────────────────┐
│ 赤春花 ▾   ↶ ↷      素材 · 歌词 · 编辑 · 样式 · 导出        │  顶栏
├───────────────────────────────────────────────────────────────────┤
│                                                                   │
│                    舞台（形态随步骤完全改变）                        │
│                                                                   │
├───────────────────────────────────────────────────────────────────┤
│ 人声分离 ▓▓▓▓▓▓░░░░ 62%  取消                                      │  任务栏（有任务才出现）
└───────────────────────────────────────────────────────────────────┘
```

- **顶栏**：工程切换、撤销/重做、步骤条。步骤条兼作进度指示——已完成的步骤打勾，
  当前步骤高亮，未满足前置条件的步骤置灰但**仍可点击**（CLAUDE.md §2.5 允许任意跳步：
  用户可能直接导入现成素材，不能强制走完流水线）。
- **舞台**：唯一的主区域，由当前步骤全权决定内容。
- **任务栏**：跨步骤常驻，只要有长任务在跑就可见。这一条保留现状，它本来就是对的。

步骤定为五个，与原先的划分有三处不同：

| 步骤 | 说明 |
|---|---|
| 素材 | **下载与分离合并成一步**。二者都是"把素材准备好"，且分离依赖已有音频；现在它们共用同一个 `MediaPanel` 只靠一个 `focusSection` 属性区分，本身就说明是一件事 |
| 歌词 | 搜索 / 导入 / 分行 |
| 编辑 | **对轴与注音合并为一步**。二者修正的是同一个选中词——一个管何时唱、一个管怎么读；且读音要靠耳朵验证，分开会让注音那步没有播放能力 |
| 样式 | **从右侧 tab 升级为独立步骤**。用户要靠它确认成片观感，窄栏里确认不了 |
| 导出 | 设置 + 结果 |

## 三点五、首页

**工程不是从某一步开始的，是从"打开哪个工程"开始的。** 应用启动时进入首页，
而不是直接落进上次的某个步骤。

首页只做两件事：**新建工程**、**浏览既有工程**。既有工程以卡片列出，每张给出
曲名、歌手、时长、最后修改时间，以及它走到了哪一步（用与步骤条一致的标记）。
点卡片进入该工程，回到它上次所在的步骤。

顶栏的工程名可点，随时回到首页。这也让"同时做几首歌"成为自然操作，而不是靠
一个下拉框硬切。

## 四、五个舞台

### 素材

主对象是**素材质量是否合格**。

左侧是获取入口（粘贴链接下载 / 拖放本地文件 / 分离档位与开始按钮），右侧上方是
**画面预览**，下方是各条音轨卡片。

画面预览在这一步是必需的：下载可能拿到坏流、可能悄悄降级到 720p、可能音画不同步，
这些问题**不看画面根本发现不了**，而一旦带着坏素材走完整条流水线，返工代价极大。
预览只需能播、能拖，不需要字幕层。

音轨卡片给出时长、采样率、文件大小，各自带独立的小波形与试听按钮——分离质量只能
靠耳朵判断。

### 歌词

**候选列表（窄）+ 大预览（宽）**，已拍板。

左列每个候选给出来源、粒度、时长、歌手，供快速扫视。中间大区域把**选中的候选按成片样式
整首渲染**——真实字体、真实配色、带注音。底部一条元信息栏汇总"逐字轴有无 / 注音有无 /
与本曲时长差多少"，以及确认按钮。

这样排的理由是：判断候选对不对，看的是**歌词内容本身**（版本混淆是 CLAUDE.md §6.1 列的头号坑，
同名不同版本的差异往往出现在中后段），纯文本列表看不出来，按成片样式渲染才能一眼认出。

歌词确认后，本舞台切换为**歌词全文编辑态**：仍是整屏渲染的歌词，但每行可拆可并、
可标记为制作名单行、可指派声部。分行不再是隐藏在别处的功能。

### 编辑（对轴与注音合并为一步）

**对轴与注音操作的是同一个对象**：对轴管"这个词什么时候唱"，注音管"这个词怎么读"，
都是对**同一个选中词**的修正。拆成两个舞台意味着同一个词要在两处各选一次。

合并还解决两个实打实的缺陷：

- **读音要靠耳朵验证。** 独立的注音舞台没有任何播放能力——确认「運命」在本曲唱
  さだめ 还是 うんめい，只能切到别的步骤去听。这本身就说明切开是错的
- **CLAUDE.md §6.2 早已要求两者共享读音表**（"注音的覆盖结果要立刻反馈给对齐器"），
  界面上却把它们隔开

形态：

```
┌────────────────────────────────────────────────┐
│ [视频预览]    歌词正文（整屏，带注音，点词即选中） │
├────────────────────────────────────────────────┤
│ 波形 + 逐字轴（选中词同步高亮）                   │
├────────────────────────────────────────────────┤
│ 走带 │ 选中「運命」 注音[サダメ] 发音[サダメ] 锁  │
└────────────────────────────────────────────────┘
```

**核心是一个选中项驱动全部**：在歌词里点一个词，它在时间轴上高亮；在时间轴上选一个词，
歌词里也高亮；检查器同时给出它的时间与读音。

保留的要点：

- 上下分割条可拖动，**默认波形占更大比例**——实际工作发生在波形上，视频只用于随时确认观感
- **tap-to-time 打轴是一等公民**（CLAUDE.md §2.5），入口在工具条上，不藏进菜单
- 每个词用下划线标出读音来源（歌词源 / 词典 / 猜测 / 手工），让"哪些是机器猜的"一眼可见
  （§7.4）。实测经验：真正让人发现问题的不是"下划线还是底色"，而是**是否与主导色形成
  异质对比**——一首歌里 98% 的词同一个来源时，四条同粗同形的实线只是四种色相
- 播放 transport 只有一个，属于本舞台

**风险**：时间轴是全应用最复杂的组件（三级调轴、tap-to-time、拖拽、拆行合并、缩放），
合并时**不要重写它**——把注音编辑接进现有的选中模型即可。

### 样式

主对象是**成片观感本身**。

中间是一块大预览，用**真实歌词的某一句**按当前样式渲染（可切换看哪一句，
默认挑一句既有汉字又有注音、长度中等的），并能播放这一句看扫色效果——
静态截图确认不了扫色和描边翻色。右侧是样式控件：预设、字体、字号、描边、
配色模板、上下行错开等。

这一步存在的全部理由就是"改了能立刻看到"，所以预览必须大、必须是真实内容、
必须能动。窄栏里的小色块确认不了任何东西。

### 导出

左侧是导出设置（ON/OFF VOCAL、是否混引导声、编码档位），右侧是产物列表：
已导出的成片、路径、体积、时长，可直接打开所在目录。

## 五、播放控制的归属

现在界面上有多处能触发播放，因为播放器是全局的、却没有明确的主人。

新规则：**音频引擎全局唯一（仍在 store 里），但 transport 控件属于舞台。**
只有素材、编辑、样式三个舞台各自拥有一个 transport，且形态不同——
素材是每条 stem 一个试听按钮，编辑是完整走带，样式是"播放这一句"。
切换步骤时上一个舞台的播放自动停止。

这样"两个播放按钮"不是靠藏掉一个来解决，而是结构上不可能同时出现。

## 六、视觉规范（深色专业工具风）

参照 DaVinci Resolve / Aegisub 一类的剪辑工具：视频画面与波形在深色底上判断更准，
且卡拉OK 字幕本身是白字黑边，深色背景更接近成片实际观感。

**应用外壳必须低饱和**，否则会和预览里的真实配色打架，用户分不清哪个颜色是成片的、
哪个是界面的。饱和色只留给来源徽章。

| 用途 | 取值 |
|---|---|
| 画布底 | `#16181d` |
| 面板 | `#1c1f26` |
| 浮层 / 卡片 | `#222630` |
| 分隔线 | `#2a2f3a` |
| 主文字 | `#e6e8ec` |
| 次要文字 | `#9aa1ad` |
| 弱文字 / 占位 | `#6b7280` |
| 交互强调 | `#4da3ff` |
| 危险 | `#ef5f5f` |

来源徽章（语义色，唯一允许的高饱和用法）：

| 来源 | 色 | 含义 |
|---|---|---|
| `provider` | `#4da3ff` 蓝 | 歌词源自带 |
| `aligned` | `#4ec9a0` 绿 | 强制对齐实测 |
| `interpolated` | `#e0b341` 黄 | 插值推算，不可当锚点 |
| `manual` | `#b78cf0` 紫 | 手工，重算时不覆盖 |

预览区域**不套用界面配色**：它必须呈现成片的真实样子，背景用工程自己的背景设定
（默认纯色兜底 `#005500`）或视频画面本身。

### 图标：一律用 Ant Design，不自己画

现在界面上的图标是零散拼凑的文字符号（`↶` `▶` `⏸` `✓`），粗细、体量、风格互不一致。

**全部改用 `@ant-design/icons`（已装，6.3.2），禁止手绘 SVG，禁止文字符号充当图标。**
理由不是省事：自绘图标必然在描边粗细、视觉重心、圆角半径上与其余部分对不齐，
而这类偏差单看每个都不明显、放在一起就是"杂乱"。用一套成熟图标库等于把这个问题
一次性消掉。

用 Outlined 系列作为默认（与深色界面的细描边基调一致），语义遵循 Ant Design 自己的
命名，不要挪用：播放 `CaretRightOutlined`、暂停 `PauseOutlined`、撤销/重做
`UndoOutlined` / `RedoOutlined`、搜索 `SearchOutlined`、下载 `DownloadOutlined`、
锁定 `LockOutlined`、拆行 `ScissorOutlined`、合并 `MergeCellsOutlined`。

图标只在**语义明确**处使用。含义依赖上下文的操作（"使用""存为模板"）用文字，
不配图标；图标加文字的组合只用于工具条这类空间紧张且动作高频的地方。

### 文案：短，且准确

界面文字**只说必须说的**。解释性的、教育性的、讲原理的句子一律不进界面——
它们属于文档。

反面例子与改法：

| 现在 | 改成 | 为什么 |
|---|---|---|
| 锁定，自动重算时不覆盖 | 锁定 | "重算不覆盖"是锁定的定义，不是需要每次重复的说明 |
| 84 MB · 先出个能听的伴奏，立刻开始调轴 | 84 MB · 最快 | 用户要的是选型依据，不是使用建议 |
| 自动轴精度约 50–150ms，够「整行同时亮起」，不够「逐字擦除严丝合缝」 | （移出界面） | 这是产品预期说明，写在文档里 |
| 使用这个候选 | 使用 | 主语宾语都在上下文里 |

三条硬规则：**按钮用动词**（使用 / 导出 / 分离，不用"确定"）；**状态用结果**
（已导出，不用"导出成功了"）；**报错说清出了什么事和怎么办**，不道歉、不含糊。

数量词、时长、体积一律用等宽数字对齐，不要在句子里夹叙夹议。

## 六点五、必须一并解决的三处结构问题

调查现状后发现三件事，不解决则光改布局仍然会"杂乱"。

### 六套并行的样式系统必须收编成一套

全局 `styles.css` 之外，歌词面板、注音编辑器、样式面板、配色选择器、时间轴**各自内联了
一套 CSS-in-JS**，类名前缀分别是 `kvm-lyric-` / `kvm-ruby-` / `kvm-style-` / `kvm-palette-` /
`kvm-tl-`。这是当初多人并行开发为避免类名冲突留下的，代价是配色、间距、圆角、字号在六处
分别维护，取值相近但互不共享变量。

**这是"杂乱"的第二个根因，与布局同等重要。** 本次重做必须建立一套设计 token
（本文第六节的色板即其基础），六套内联样式统一改为消费这套 token。允许组件保留自己的
布局细节，但**颜色、间距刻度、圆角、字号、边框一律不得再出现字面量**。

### 歌词的"成片样式渲染"目前没有现成能力

真实的所见即所得渲染只存在于视频预览里，走 JASSUB（libass 的 WASM 构建），而它**必须挂在
一个真实的视频元素上**，无法脱离出来当作独立的文本卡片使用。配色选择器里那个取样预览是
CSS 模拟，没有逐字扫色、没有注音排版，只能用来判断两个颜色搭不搭。

因此两处新舞台的渲染方式**分别决策**：

| 舞台 | 渲染方式 | 理由 |
|---|---|---|
| 歌词候选大预览 | CSS 近似（原生 ruby 标注 + 文字描边） | 这一步要判断的是**文本内容与版本对不对**，不是像素级观感；CSS 近似不依赖视频元素、切换候选零延迟 |
| 样式舞台大预览 | 真实 JASSUB 渲染 | 这一步的**全部意义就是确认成片观感**，用近似等于没确认。需要把字幕渲染层改造成可挂在独立的画面元素上，而不是只能挂主预览 |

### 声部配色改了不保存

配色编辑目前停留在组件内部草稿态，刷新页面即丢失——状态层其实已经有对应的保存动作，
只是样式面板从未调用它。重写样式舞台时**顺手接上**，不要照搬现有的草稿态实现。

## 七、这次重做保留什么

以下已验证的资产不动，只是换个位置或换个容器：

- 后端全部 API 与数据模型
- 波形渲染（wavesurfer）、JASSUB 预览绑定、ASS 配色换算、假名处理等库层能力
- 任务栏与长任务进度协议
- 崩溃恢复与撤销/重做的既有行为

需要重写的是外壳与各步骤面板的组织方式，以及全部样式。

## 七点五、每个舞台都会踩的一个坑：flex 高度链

各舞台都是"外层不滚、内部分区各自滚"的结构。这个结构有一个**必然会踩且症状具有误导性**
的坑，实现新舞台时先看这里。

**纵向 flex 的子项，`min-height` 默认是 `auto`——意思是"不得小于内容的最小高度"。**
所以一个装着 60 行歌词的容器会把自己撑到三千多像素，它内部那个写了 `overflow-y: auto`
的元素跟着被撑开（`clientHeight === scrollHeight`），于是**永远不会变成滚动容器**；
溢出一路上交到最外层被裁掉。

症状是"内容滚不动、后半截看不见"，而**排查时最容易怀疑的 `overflow` 设置其实是对的**。
断链发生在更上层某个漏了 `min-height: 0` 的祖先上。

两条实践：

- **凡是"占满剩余高度并把滚动交给子元素"的纵向 flex 子项，一律显式写 `min-height: 0`。**
  不是保险起见，是这个结构的必要条件
- **排查时逐层打印 `clientHeight` / `scrollHeight`**，第一个二者相等且大于视口的祖先就是断点。
  只看某一层的 `overflow` 判断不出来

同一个组件在不同形态下可能不暴露这个问题：子项落在**交叉轴**上时高度由 stretch 给定、
与内容无关，怎么写都正常。所以"换个态就好了"不是巧合，两条取高路径本来就不同——
**每个形态都要单独验证能滚**。

## 八、尚未决定的事

- **注音舞台里 token 的来源标记用底色还是下划线**：底色更醒目但会和"已唱/未唱"的
  预览配色抢视觉；下划线更克制但小字号下不易察觉。实现时先做下划线，
  真机看过再定，若不够醒目则改为底色并把预览配色降饱和。
- **样式舞台的预览用 JASSUB 实时渲染还是后端出单帧**：实时渲染能看扫色，
  代价是每次改参数都要重建字幕轨；单帧快但看不到动效。当前假设是用 JASSUB 实时渲染，
  若实测单次更新延迟过高，则改为"拖动参数时用静态近似、松手后再实时渲染"。
- **步骤条上"已完成"的判定标准**：目前假设按"该步骤的产物是否存在"判定
  （有音频即素材完成、有歌词行即歌词完成、有非插值时间轴即对轴完成）。
  若实际使用中出现误判为完成的情况，改为显式的用户确认。
